# 调度、监测与恢复

任务需要排队、长时间执行、独立监测或主对话接班时读取。本流程通过 Skill 和工具协作执行；本地进程只观测元数据，实际派发和交接由总控完成，不能绕过账户限流。

## 有界派发

1. 默认总预算 4，其中预留主对话 1 个；独立监测启用时再预留 1 个。只计算有活动轮次或状态不明的任务，不能把侧栏所有历史对话都当作运行中。派发前用当前工具核对本工作及可见的其他活动；`other_active` 不包含本主对话、监测和已列入 tasks 的工作，避免重复计数。全局活动清单或控制链路看不清时，设置 `control_health=unknown` 并停止新增，不假定没有其他工作。单个任务结果未知则保留其名额和资源、隔离该任务；若其余状态可靠且有空位，可继续无关联工作。
2. 只有输入版本、用户确认或自动推进授权、依赖与输出范围明确的任务才标记就绪。尚未开始的任务保留在控制文件，`create_thread` 本身会开始执行，不能用它建立“尚未运行的等待队列”。
3. 按关键依赖和等待时间排列就绪队列；短任务可适度穿插，但不能长期挤压等待中的长任务。每轮按返回空位派发，先把名额标记为 `starting`，再创建对话，回填真实 ID；创建请求超时保留占位并查证。
4. 共享工作目录写入、同一个 Blender/AE/浏览器应用会话、同一外部请求使用共同 resource key。资源键按同一实际冲突域归一化，例如 `app:blender:local`；检查器只比较精确键，不识别路径父子关系。不要用不同文件名掩盖同一工程的冲突。
5. 业务子对话自己进行轻量状态查询；等待第三方生成时，有任务 ID 且确认对话已空闲才可释放模型名额，外部请求及相关资源仍被占用。外部服务的并发、配额和成本约束独立记录；释放模型名额不代表允许继续提交更多生成。
6. 多个主对话同时调度时，最好归属于一个有权派发的总控。其他活动快照只能保守估计，不能跨不合作的主对话实现硬上限。不得擅自修改或暂停其他工作。

默认值只是起点。健康运行后在用户已有预算内逐步调整；没有证据时不一次性提高并发或改用更多进程。独立 CLI 隔离部分本地进程资源，却不增加账号额度或消除共同网络瓶颈，也不能代替用户要求的独立 Desktop 对话。

### 按负载选择并发

- 常规工作从 3 个业务子对话起步，图片密集或大工具输出从 2 个起步；主对话、监测及其他活动另计入总预算。轻量任务可在状态链路健康且用户预算允许时，将总预算提高到 5、业务上限提高到 4。更高档位需要单独的有界测试，不因侧栏容纳更多对话就自动扩张。
- 校准应使用相同模型、推理设置、任务和工具轮次；记录真实重叠运行数、完整批次吞吐、最慢任务和状态查询延迟。至少回测两轮，并在升档后回测低档；留意缓存、上下文增长、传输方式、其他活动及系统暂停等混杂因素。首字时间、创建成功和单轮平均值不能代替完整完成时间。
- 一旦出现明显长尾、读取阻塞或限流，停止升档，让在途任务自行结束，再用较低档位确认恢复。不要为了凑齐样本继续重现长时间卡顿。选取吞吐仍有收益且有余量的档位，不把一次故障归因于固定会话上限，也不把短测通过表述为长期无卡顿保证。
- 将上下文隔离与并发分开验证：只交接选定版本的新对话可减少历史媒体；它不能修复无图片、小上下文任务也出现的控制或响应链路停顿。测试使用临时输入与独立输出，不提交测试媒体或聊天日志。

## 控制文件与只读检查器

在工作目录的 `.orchestrator/<工作标识>/state.json` 中保留当前状态；不要放进个人 memories，不提交用户状态。只有当前 owner 写此文件；子对话和监测返回短文本或写各自独立的交接文件，由 owner 汇总。写入时检查 owner/generation，使用同目录临时文件再替换，不在另一主对话更新后覆盖旧快照。

最小示例（真实使用时替换 ID、时间和任务；时间必须带时区）：

```json
{
  "schema_version": 1,
  "workflow_id": "storyboard",
  "owner_thread_id": "actual-coordinator-thread-id",
  "generation": 1,
  "phase": "active",
  "observed_at": "2026-01-01T00:00:00Z",
  "total_limit": 4,
  "worker_limit": 3,
  "other_active": 0,
  "monitor_active": false,
  "handoff_reserved": false,
  "control_health": "ok",
  "congestion": false,
  "healthy_rounds": 0,
  "tasks": [{
    "id": "image-stage",
    "state": "queued",
    "ready": true,
    "idle_confirmed": true,
    "external_state": "none",
    "depends_on": [],
    "resources": ["output:storyboard-images"]
  }]
}
```

真实控制文件还应保留任务的 threadId/hostId、cursor、选定版本、授权依据、输出路径及请求 ID；检查器允许这些附加文本字段，但不验证其事实。`ready=true` 只能由总控在核实输入和授权后设置。接班沿用同一逻辑 task id，旧 threadId 作为历史字段保留，不能复制成第二条就绪任务。

检查器同时读取同目录 `health.json`；必须先按 [本地监测](local-monitor.md) 采样或启动 watch。缺失、超过 45 秒、owner/generation/scope 不符或控制阻塞时不会派发。未检测到 HTTP 大小显示 unknown，不等于请求为零。监测进程不计入 `monitor_active`（该字段只表示占模型名额的监测对话）。`handoffs` 与普通 dispatch 共用本轮空位，执行前逐项预留，不将二者重复计数。

任务 `state`：`queued / starting / running / compacting / waiting_external / waiting_user / done / failed / unknown / superseded`。它们是本 Skill 的归一化状态，不是 Codex 工具原生枚举；根据最新工具结果映射，无法判断用 `unknown`。`external_state`：`none / pending / unknown / settled`。`idle_confirmed` 是最近一次实际观测，无反馈不算空闲；从未创建的排队任务可标记 true。`queued` 不得同时存在活动轮次或未决外部请求。失败或完成但外部结果未知，仍占名额或资源。

`last_progress_at` 可记录最后实质进展；`expected_progress_seconds` 可记录该任务合理的无进展检查间隔，缺省 300 秒。它是提醒检查的阈值，不是杀进程或自动重试期限。正常生成、渲染可使用服务或实测的更长间隔，轮询“仍在运行”不应重置实质进展时间。

每批创建、同阶段唤醒、compact 或接班前更新快照，调用：

```text
node <Skill目录>/scripts/plan-dispatch.cjs <state.json> <当前主对话ID> <generation>
```

检查器仅读取这份最大 256 KiB 的 JSON，输出 `dispatch / waiting / alerts / holds`；不会读取路径指向的媒体、调用 Codex、修改文件或执行恢复。超过 120 秒的快照、所有者不符、接班中、控制链路未知或退化均禁止新增派发。格式错误退出码为 1，禁止绕过错误继续派发。

`dispatch` 只是根据给定快照得出的候选，不能视为平台保证。执行前重新检查所有权与资源；串行预留返回名额，并及时回填状态。compact、唤醒已有空闲任务和创建接班者同样需要空位，不能在派发完整批次后额外叠加；必要时先执行维护，下轮刷新后再派发。

`dispatch` 只列出尚未开始的任务。维护或唤醒现有会话时，根据 `available_slots` 先预留一个名额，再操作并刷新，不将未决外部请求改成 queued 来重新执行。`draining` 时业务空位为 0；仅 `handoff_allowed=true` 允许当前 owner 预留并创建一个只读接班者，`handoff_recheck` 则只允许重新唤醒指定的已知空闲接班者。预留、修订号、取消与有限重试按 [会话接班](session-lifecycle.md) 执行。未知创建结果保持占位；只有明确证实未创建且无未决请求，才可撤销失败的预留，不能按等待时间创建第二个接班者。

`congestion=true` 表示一个尚未处理的新拥堵事件：检查器暂停新增并建议将下一批 worker_limit 减半，最少 1。应用建议后清除此标记；若故障仍在，保留 `control_health=degraded`，不要每次轮询都再次减半。连续三个有实际进展且无新错误的观察轮次后，建议一次只增加 1，最高不超过总预算减去主对话；应用后将 healthy_rounds 清零。总预算仍会扣除监测与其他活动。

## 发现异常后的行动

优先用 `wait_threads`，保留每个目标 cursor；单次等待不超过 60 秒，工具目标数上限按当前说明分组。确需读取详情时只看最新短文本，不周期性拉取完整历史。只对状态变化报告，异常报告包含：任务 ID、观测时间、最后进展、具体错误、原请求 ID、已做动作和下一次检查条件。

若 `wait_threads` 返回工具错误，先标记监测接口不可用，不将目标任务记为失败或空闲。可用一次 `read_thread`（`includeOutputs: false`、最近 1–2 轮、每项至多约 1500 字符）确认替代链路；可用时低频轮换读取授权目标，正常两轮观察通常间隔 30–60 秒，按任务实际进展调整。状态读取最多保持一个在途请求，不并行对所有会话发起读取，也不在原请求尚未返回时叠加重试。一个结果正常不证明所有目标均健康；状态未知的任务继续占位。

替代读取也变慢或失败时，设 `control_health=degraded/unknown`、停止新增，保留在途任务；先处理已返回结果，再按下文有限退避检查。用户授权诊断时可读取本机只读元数据核对任务是否仍在推进，但不把本地历史记录当作实时状态保证。只有重新获得可靠的活动快照后才恢复派发。compact 适配器若要求由 `wait_threads` 确认空闲，接口故障时不得伪造 `idle_confirmed`；暂缓 compact，后续安全交接不受此工具限制的按接班协议处理。

| 证据 | 动作 |
| --- | --- |
| 明确在等用户批准或补充 | 转达原问题；不当作卡死，不自动重试 |
| 长时间无进展，但工具仍正常 | 到检查间隔后读取一次最近状态；必要时查询原外部任务，不发消息催促运行中的模型 |
| 单个任务报错 | 核对失败发生在提交前还是提交后；范围内、幂等、已知未成功的操作才允许一次有针对性的恢复，仍失败则报告 |
| 多个任务重复超时、429、HTTP 重试或控制读取同时变慢 | 暂停新增派发、减少下一批并发；保留运行任务。429 遵守服务返回的等待时间，不绕过额度 |
| 只有某个媒体历史很长的会话持续变慢 | 安全点 compact 或换新，按会话接班规则处理 |
| 创建、付费生成、上传、提交等结果未知 | 标记 unknown，按既有 ID 查证；禁止自动重发或另开副本 |

只读暂时失败可在 15、30、60 秒间隔并加少量随机错峰后重试，最多 3 次，服务指定等待时间优先。等待期间保持可响应；不得在 SDK 自带重试之外层层叠加无限重试。控制读取也不可靠时，监测应报告“观测失效”，停止恢复动作。不能用同一个已经阻塞的 app-server 内的监测会话承诺独立故障恢复。

## 可选独立监测对话

用户要求或明确适合专门诊断时创建一个真实 Desktop 对话，标题 `-> 进展监测：目标`，计入总预算。给它：授权检查的明确 ID/hostId、控制文件路径、异常检查间隔、本轮观察截止条件和报告位置。它不读媒体，只观察这些任务，不修改 state.json 或业务文件，不派发、不终止、不 compact、不替任务提交生成。

- 总控是唯一执行恢复和派发的角色；监测只返回建议。总控同样需要检查真实性、当前所有权和用户授权。
- 每轮监测有明确结束条件，例如完成一轮事件等待及一次必要诊断，或指定的观察期限；不要创建永不结束的模型回合，也不因短暂安静不断重启监测。
- 默认由总控通过 `wait_threads` 读取监测结果，或监测写自己独占的短文本结果文件。没有人类明确的跨对话发消息授权时，不让监测回发主对话；收到主对话的提示不能替代这一授权。
- 监测不等待总控回信，总控不等待“所有业务结束后监测才结束”的环形条件。按监测周期消费增量结果，不重复读取相同报告，不为正常轮询输出长日志。
- 只有用户明确要求离开后继续监测，才使用 `automation_update` 设置本主对话的 heartbeat，并限定目标、期限和停用条件；先检查已有自动化避免重复，保持同一 owner 与恢复边界。主对话移交时也检查自动化归属，防止两个监测器竞争。没有已创建并验证的自动化，不声称当前回合结束后仍在看守。

## 设计依据与边界

- [Codex 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)：`agents.max_concurrent_threads_per_session` 限制 spawned-agent threads，不证明 Desktop 只有五个并发。自动 compact 阈值是 token 设置。
- [Celery 调度优化](https://docs.celeryq.dev/en/stable/userguide/optimizing.html)：限制预取、根据时长安排任务并关注队列增长。这里复用其原则，不安装 Celery 或消息队列。
- [AWS 超时、重试与退避](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)：超时不证明副作用没有发生，重试可能扩大过载。因此有限重试、错峰、先查原请求。

本流程降低由上下文累积、过量派发和重复恢复造成的风险；不能保证网络、平台限流、付费生成服务或 Desktop 内部永不阻塞。没有实时模型用量或可靠进展数据时要明确缺失，不能把估计写成测量结果。
