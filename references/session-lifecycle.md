# 会话接班与 compact

仅在上下文维护、阶段切换或主对话接班时读取。目标是只携带仍然有用的状态继续工作，不能把“已丢弃历史”当作事实，更不能丢失用户约束、预算、授权和进行中的外部请求。

## 选择处理方式

| 当前情况 | 处理 |
| --- | --- |
| 同一问题的推理仍重要，以文本为主 | 优先继续原会话，必要时在空闲时 compact |
| 新的可独立验收阶段，或仅选定结果有用、旧媒体历史已无用 | 新建会话，只交接选定版本与有效约束 |
| 同阶段反复读图后延迟增长，旧媒体已无用，或 compact 后仍慢 | 在安全点换新会话，无需先等 token 阈值或强制先 compact |
| 生成、上传或写入结果未知 | 先查询原请求状态；只读诊断，不另开会话重做 |
| 已完成且不会继续的旧任务 | 保留即可，不为“清理”额外调用模型 |

本地监测达到 20MB 时提醒并准备交接；达到 25MB 时不再为该上下文添加后续阶段，在安全节点按下述协议换新。使用未压缩 HTTP 请求体字节，详见 [本地监测](local-monitor.md)。选择已明确且授权覆盖剩余工作时直接交接；不因换聊天再次索要同一许可。选定版本存在歧义才询问用户。技术信息缺失先向子对话补齐；尚未核实外部请求时不换新重做。控制链路阻塞期间暂停接班创建，先保留交接状态。

原生 token 阈值是自动 compact 的触发配置，不是定时维护器或媒体字节上限。不根据聊天文件总大小猜当前有效 token 数，也不宣称修改配置立即刷新已有运行会话。若当前用量可观测，可在接近阈值、准备大批读图前先到安全点交接；无可靠指标时按阶段和实际延迟决策，不编造用量。

## 最小交接包

仅需保留当前状态，不复制旧对话，不 fork。简单子任务可直接使用短文本；主对话接班用工作目录中的控制文件和 `handoff.md`，通常几 KB 即可，超长时将必要文字详情留在独立文件按需读取。

- 目标、完成标准、仍有效的用户约束、用户授权的具体范围及可核实依据；不要把旧代理的自述升级为用户授权。
- 选定版本的准确绝对路径、版本标识、输入版本、验证结果、用户确认状态；候选版本只在仍是必要参考时列入。
- 当前任务 ID、真实 threadId/hostId、依赖、写入范围或占用的应用、未完成事项、等待用户的决策。
- 外部请求 ID、提交时间、已知状态、结果查询方式；恢复应使用既有请求，不把提交超时等同于未提交。
- 当前并发预算、队列、最近异常、cursor、主对话 ID 和 generation；状态来源与更新时间。
- 必要的脚本、工程、备份路径，不能只有一张结果图而丢掉可继续编辑的源文件。

媒体路径只作为文本；文件链接不要求读取媒体。接班对话按职责读取需要的文件，总控仍不查看图片、视频或截图。

## 子对话换新

1. 子对话在阶段结束或安全点返回 `建议换新` 和交接包，结束本轮，不自行创建下一层子对话。
2. 总控读取最新短文本并确认旧对话空闲、无未核实的写入或外部提交。已知外部请求仍运行时，可以交接查询职责，但新对话只能查询该请求，不能再提交相同生成；未知状态先留在原任务中核实。
3. 预留新对话名额，用 `create_thread` 创建接班者。标题保留任务含义，可加 `续 2`；提示词只给交接包、选定路径和剩余工作。
4. 创建返回真实 ID 后更新任务映射，旧对话标记为历史来源；创建结果未知先查证，不重复派发。新对话沿用同一逻辑任务 ID，不把接班算成第二份工作。
5. 用户回到旧对话提出更改时，旧对话先核对当前负责人，说明接班入口；在获得通信授权后转交新要求。不能继续写入同一产物或把用户未确认的新版本静默送入下游。

## 主对话换新：准备、确认、提交

需要已获得用户对新主对话继续管理本工作及相关任务的授权。Skill 不能替用户授权跨对话发消息；若新主对话只能读取现有任务而通信授权无法核实，先完成只读接收，说明缺失的具体权限后再请求，不能伪装成已拥有调度权。

1. **准备**：旧总控停止新增派发，将控制文件 `phase` 改为 `draining`；正在执行的子任务继续工作，不必全部中断或等待其结束。记录当前状态与更新时间，写好最小交接包和 `handoff_revision`；不在此时压缩旧总控自身。
2. **接收**：检查器返回 `handoff_allowed=true` 时，先设置 `handoff_reserved=true` 并登记接班任务（`role=standby`、`target_generation=当前代次+1`、`state=starting`、`idle_confirmed=false`），将其 ID 写入 `successor_task_id`，再创建一个全新主对话，使用 `🌟 原目标 · 续 2` 等清晰标题。回填实际 thread_id。接收回合同样占一个活动名额。它先以 standby 身份只读控制文件，检查必要信息，输出 `READY + workflow_id + generation + handoff_revision` 后结束本轮；此时不派发、不修改控制文件、不向任何子对话发消息。它不必等待旧总控回复。
3. **核对**：旧总控用 `wait_threads` / `read_thread` 核实 READY、交接修订号与实际新主对话 ID。确认接收轮次结束后将接班任务标记 done/idle。刷新子任务状态和用户新增指令；若版本、队列或约束变化，更新交接包、递增 handoff_revision，在检查器返回该任务的 `handoff_recheck` 时重新预留名额，只唤醒同一个已知空闲接班者做只读核对。不得为复核另建主对话。新主对话未就绪时仍由旧总控保管状态。
4. **提交所有权**：旧总控一次性将 `owner_thread_id` 更新为新 ID、`generation` 加一、`phase` 改为 `active`。接收回合确认结束后标记完成，解除其占位；清除新一代的 handoff_reserved 和 successor_task_id，记录本次已移交。使用同目录临时文件再替换，只有旧总控写这次移交。之后旧总控永久停止业务派发，保留为历史入口。
5. **继续**：有用户通信授权时，由旧总控向新总控发送一次“已提交，读取 generation N 后继续”；否则让用户直接到新入口继续。新总控每次派发或恢复前，检查文件 owner 与 generation，再核对真实任务状态；旧总控本轮尚未结束时也计入其他活动。创建/通知结果未知先查证，不能产生第二个接班者或第二次业务提交。

创建结果未知时保留预留，只查证。若有明确证据表明创建在派发前失败、没有候选对话也没有未决创建请求，才可将接班任务标记 failed/idle，清除本次预留和 successor_task_id；修复具体原因后最多重试一次，或取消移交、由旧 owner 恢复 active。已创建的空闲接班者优先复用；其内容不满足 READY 时沿原对话修正，不另开副本。证据不足就报告，不能按超时自动清预留。

移交后若新总控无响应，旧总控只做只读查证并报告；不可根据时间自动夺回所有权。恢复需要确认接班者空闲并明确移交，避免两个总控同时工作。控制文件是协作约定，不是平台强制锁；多个互不协作的主对话不能靠同一份快照获得可靠的全局并发限制。

保留旧对话和文件，不删除、不自动归档。用户以后在旧主对话发言时先检查 owner，指向新主对话，或在明确授权后转发指令。向用户提供真实的新主对话入口，不能宣称 UI 已自动迁移。

## 主对话 compact

- 当前正在回复的主对话不满足空闲条件，不调用 `compact_thread(..., idle_confirmed=true)` 压缩自己。
- 依赖原生自动 compact，或在本轮结束后由用户使用客户端支持的 compact 操作；若使用另一个授权管理对话，仍须先确认目标空闲、保存交接包，并验证 `contextCompaction` 完成。
- 不新建常驻模型仅为定时 compact。compact 失败、结果未知或历史媒体仍影响性能时，按上面的接班流程继续，不循环重试。

设计借鉴 [Temporal Continue-As-New](https://docs.temporal.io/develop/go/workflows/continue-as-new)：将当前状态传给具有新历史的下一次执行。这里是工具与文件组成的协作协议，不具备 Temporal 的原子执行保证。Codex 的 compact 与 coherent unit of work 建议见 [官方最佳实践](https://learn.chatgpt.com/guides/best-practices)。
